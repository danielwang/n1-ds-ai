# Generation and implementation workflow

Read for new N1 interfaces or changes to an existing implementation.

1. Complete [implementation preflight](implementation-preflight.md). Establish the user's task, audience, target platform, required states, and requested deliverable. Use the [product context and principle](system/foundations/design-principles.md). Avoid adding unrelated flows or treating every listed audience as a required role model.
2. Inspect existing project components, dependencies, styling, and tokens before coding. Find the applicable N1 source component through the [index](system/components/index.md). Read its purpose/usage status, anatomy, properties, variants, token observations, and known gaps. Use the actual member list to verify a proposed combination exists.
3. Map Figma configuration to real code only after inspecting that implementation's imports and API. Prefer applicable approved components; otherwise reuse the closest verified N1 structure and disclose its approval gap. An isolated implementation from source details is an option only when compatible with the user's constraints. If substitute implementations or framework selection are prohibited, request the missing project/package instead. A missing Code Connect map does not authorize inventing an API or claiming N1 approval. Optionally verify a Figma variant selection with `scripts/check_selection.py`; this checks source combinations, not runtime APIs.
4. Apply value-bearing definitions from the [token snapshot](system/tokens/README.md) or attributable component evidence within their verified context. Preserve original names, units, aliases, and modes when exposed. Do not convert discovered spacing names into values, assume global theme roles, or fill absent modes. A required unsupported value remains a labelled local proposal, not a new shared token.
5. Consult [patterns](system/patterns/index.md), [voice and tone](system/foundations/voice-and-tone.md), and [accessibility](system/foundations/accessibility.md). Apply explicit requirements where available. Mark decisions about undocumented focus, dismissal, validation timing, breakpoints, or AI transitions as **Needs design review**; any chosen implementation behavior is a disclosed proposal.
6. Compare the result with the selected source member and actual code behavior. Verify relevant states, source-backed dimensions/style choices, token usage, copy, and documented requirements, including an explicit target supplied for this task. Test actual contrast pairs; token names alone do not establish compliance or a disabled-state exemption. Run project checks appropriate to the change; distinguish tested behavior from visual or structural observations. Do not claim a compliance test that was not performed.

Explain the selected component/node and actual variant, implementation reference, token sources, deviations, and unresolved decisions in the handoff. Attach proposals to their task context rather than modifying the bundled snapshot or global policy. For fresh source details, follow [Figma refresh](figma-refresh.md).
