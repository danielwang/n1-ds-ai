# Maintenance and packaging

Read [source authority](../AGENTS.md) and the [publishing checklist](publishing-checklist.md) before preparing updates. Technical checks do not approve design changes.

## Ownership and generation

| Material | Maintenance | Required review |
| --- | --- | --- |
| `design.md`, `foundations/`, `patterns/`, usage/voice guidance | Authored, approval-labelled | Design/product owner |
| `sources/figma/` evidence | Read-only official MCP sampling; REST proposal described separately | Source scope, freshness and confidentiality |
| `tokens/*.json`, token-evidence `coverage.json`, source manifest extraction fields | `scripts/build_tokens.py` from retained token evidence | Names, values, gaps and provenance |
| `components/`, component inventory/coverage audits | `scripts/build_components.py` from retained component evidence | Visual structure, coverage and removals |
| Skill `SKILL.md`, helpers and workflow references | Authored workflows; never duplicate design values | Design/engineering |
| Skill `references/system/`, snapshot manifest | `scripts/package_n1_skill.py` | Copied references, hashes and approval labels |
| Local ZIP and checksum | `scripts/package_n1_skill.py --zip` | Confidentiality and distribution permission |

Other audit reports, token README and root/foundation/pattern guidance are not regenerated by these commands. The generators do not invent usage rules or component APIs. The legacy `skills/nebulaone/` staging directory is not the installable package.

## Review an evidence update

1. Use a working branch. Verify current Figma file access before fresh MCP extraction. Store only approved read-only evidence with source arguments, tool/API, observation time and result. Inspect errors and coverage before generating.
2. Run `python3 scripts/build_tokens.py` and `python3 scripts/build_components.py` for the existing MCP evidence format. These are offline, deterministic builders. They cannot consume a REST variable export without the reviewed conversion proposed in [Figma synchronization](figma-sync.md).
3. Review additions, renames, removed sources, conflicts and scope. The component generator intentionally does not silently delete old component documents; if entries were removed or renamed, identify obsolete filenames from the old index and remove those generated documents explicitly in the same review. Validation rejects excess documents.
4. Run `python3 scripts/package_n1_skill.py` to refresh bundled references. It computes the complete reference closure before copying and prunes only obsolete paths owned by the previous manifest. Unknown files in that generated area stop the refresh.
5. Run `python3 scripts/validate_repository.py`. Inspect diffs and assign design and engineering reviewers. Commit only after checks pass; push/create a remote PR only when the destination/action is authorized.
6. After approval, build the ZIP locally and review confidentiality before sharing it. No workflow uploads assets, creates releases or publishes the ZIP.

If generation fails, stop and inspect the diff before rerunning. Scripts are not transactional across the whole repository. They are intended for working branches; use Git to review/revert specific generated paths, keeping unrelated user work intact.

## Validation contract

The single validation command rejects duplicate JSON keys and non-finite values; checks current token types, counts and retained provenance; verifies catalog identities/properties; checks inline local Markdown links/heading anchors and required files; compares fresh generation in a temporary copy; verifies canonical-to-bundle hashes and packaged references; parses Python; and runs maintenance regression tests. It checks common credential patterns without printing values. External links, arbitrary Markdown reference-link syntax, confidentiality classification, live Figma freshness, design approval and browser accessibility are outside these checks. Run an organization-approved secret/history scanner before first publication; the narrow built-in scan is not a replacement.

Existing token validation intentionally targets the partial MCP snapshot, including unknown aliases/modes. A full REST conversion needs its own contract and reviewed migration; do not weaken checks merely to accept different data.

The skill's standalone validator uses original source counts and identities, not fixed historical component/color totals. Snapshot dates derive from the recorded access verification; individual evidence retains its own observation times. A rebuild does not claim a fresh Figma observation.

## Reproducible package

The ZIP uses sorted relative paths, a single directory root, fixed 1980 timestamps, Unix mode 0644 and compression level 9. It excludes caches and rejects symlinks and credential-like inputs. `--zip` checks snapshot freshness and validates the skill without implicitly changing references. `--output PATH` chooses another local archive destination. Identical inputs and Python/zlib versions produce identical bytes; cross-zlib byte identity is not guaranteed. The checksum is regenerated alongside the archive. Maintenance tests compare two builds and verify archive membership.

## GitHub configuration

[Validation workflow](../.github/workflows/validate.yml) runs on pull requests, pushes and manual dispatch with read-only permissions, no secrets and no artifact upload. It uses SHA-pinned checkout and the Python supplied by Ubuntu 24.04; there are no pip downloads. It builds a local ZIP only after validation.

[Update workflow](../.github/workflows/update-generated.yml) is a separate manual, draft-PR workflow. It is inert until `N1_ENABLE_UPDATE_PRS=true`, the repository is private, the dispatch is on its default branch and the operator confirms authorization. Create the `n1-maintenance` environment with required reviewers first. The workflow checks out committed default-branch evidence, regenerates only owned output paths, validates before committing, pushes a unique branch and opens a draft PR. It fetches no new Figma data and never overwrites authored guidance, auto-merges, or publishes assets. Do not enable it before destination and push authorization.

Enable “Allow GitHub Actions to create and approve pull requests” only if organizational policy permits the draft-PR workflow. It does not approve PRs. A `GITHUB_TOKEN`-created PR may not trigger ordinary PR CI: manually dispatch validation against the proposal branch and require its successful check before merging. No personal token is required by the prepared workflow. No schedule is configured. Actual branch protection, reviewer identities/CODEOWNERS and environment restrictions require repository-owner setup after the destination is chosen.

Action pins and runner versions should be reviewed periodically through dependency-update PRs. The current checkout pin is [the verified v4.2.2 commit](https://github.com/actions/checkout/commit/11bd71901bbe5b1630ceea73d27597364c9af683); it is not a claim to be the newest version. Workflow permissions and event separation follow [GitHub's secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use).
